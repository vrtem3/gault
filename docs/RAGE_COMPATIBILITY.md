# rage, logN=19–20 и бюджет памяти

Анализ от 19.10.2026. Криптографические параметры и браузерный предел сохранены. В последующем разрешённом [прогоне 10 ГБ](TESTING.md#разрешённый-синтетический-прогон-10-гб--19102026) установленный rage выбрал logN=19: age/rage восстановили весь файл с совпадением SHA-256, браузер корректно отказал по пределу 18. Поддержка 30 ГБ не проверялась.

## Причина ограничения

Это различие ресурсных политик, а не несовместимость формата age v1. [rage 0.12.1](https://github.com/str4d/rage/blob/v0.12.1/age/src/native/scrypt.rs) калибрует scrypt примерно на секунду работы конкретного устройства. Наши неизменяемые образцы rage получили logN=19 для пустого входа и logN=20 для остальных четырёх входов. Gault останавливает их своим фильтром logN≤18 до вызова KDF.

[Typage 0.3.1](https://github.com/FiloSottile/typage/blob/v0.3.1/lib/recipients.ts) умеет читать scrypt до logN=20 и вызывает стандартный scrypt с r=8, p=1. В закреплённом `@noble/hashes 2.4.0` рабочие буферы занимают `128 × r × (2^logN + p + 1)` байтов; встроенный `maxmem` равен 1 ГиБ + 2 КиБ. [Исходник noble](https://github.com/paulmillr/noble-hashes/blob/2.4.0/src/scrypt.ts) и установленная зависимость проверены; версия 2.4.0 уже содержит исправление учёта памяти для logN=20. Подменять библиотеку или править `node_modules` не требуется.

| logN | Основная таблица scrypt | Таблица и два рабочих блока noble |
|---|---|---|
| 18 | 256 МиБ | 268 437 504 байта = 256 МиБ + 2 КиБ |
| 19 | 512 МиБ | 536 872 960 байтов = 512 МиБ + 2 КиБ |
| 20 | 1 ГиБ | 1 073 743 872 байта = 1 ГиБ + 2 КиБ |

Это расчёт буферов конкретной реализации, **не предел RSS браузера**: отдельно нужны память движка, вкладки, Worker, код, буферы потока и ОС. Память KDF не зависит от размера файла. Маленький `.age` тоже может потребовать 1 ГиБ. Объём буферов дополнительно подтверждён вызовом проверки `maxmem=0`: библиотека отказала до выделения рабочих буферов и вернула ожидаемые значения. Это не замер потребления RAM при выполнении KDF.

Потоковая обработка ограничивает память содержимого, но не устраняет таблицу scrypt. Worker сохраняет отзывчивость интерфейса, однако использует память того же компьютера и может быть аварийно остановлен браузером. У Typage нет публичной настройки общего бюджета RSS; `setScryptWorkFactor` относится к **шифрованию**, не к чтению чужого файла.

## Рекомендуемое решение сейчас

Сохранить шифрование Gault с logN=18 и обычное браузерное чтение до 18. Контейнеры с 19–20 восстанавливать локально официальным age/rage на ПК с достаточной свободной памятью, сохраняя исходные параметры. Образцы уже восстановлены независимыми CLI с совпадением SHA-256; нативный Windows-прогон ещё предстоит.

Для rage можно явно ограничить стоимость чтения двадцатым уровнем. Пример для macOS, когда CLI установлен в PATH:

```bash
rage --decrypt --max-work-factor 20 --output "./restored.bin" "./archive.bin.age"
```

Для Windows PowerShell, если `rage.exe` распакован в текущую папку:

```powershell
.\rage.exe --decrypt --max-work-factor 20 --output ".\restored.bin" ".\archive.bin.age"
```

Назначение должно быть новым файлом. Фраза вводится в запрос самой программы; её нельзя вписывать в команду. `--max-work-factor 20` проверен по справке CLI и [ветке расшифровки rage](https://github.com/str4d/rage/blob/v0.12.1/rage/src/bin/rage/main.rs): это верхний предел допустимого logN при чтении. Он не меняет KDF файла, не понижает его стойкость и не задаёт logN для нового шифрования. Пример PowerShell требует запланированного нативного подтверждения на Windows.

CLI также требует память и место для результата. При нехватке ресурсов перенесите восстановление на подходящий ПК. Не удаляйте `.age`; неполный результат после ошибки не считается восстановленным. Окончание команды должно быть успешным, а SHA-256 результата — совпадать с доверенным оригиналом или ранее сохранённой суммой. Дополнительные правила: [RECOVERY.md](RECOVERY.md).

Нельзя заменять число 20 на 18 в заголовке: KDF и аутентификация перестанут соответствовать файлу. Перешифровка с меньшим KDF ради совместимости снижает стоимость перебора и не предлагается как решение.

## Возможное расширение браузера — отдельная будущая задача

Если требуется именно rage → Gault для 19–20, минимальный вариант — **явно включаемое чтение на ПК**, без изменения формата, библиотеки и новых шифрований. Архитектура File → существующий Worker → дисковый sink сохраняется. Потребуются раздельные константы для шифрования (18), обычного чтения (18) и абсолютного потолка чтения (20), а также один проверяемый параметр разрешения в текущем протоколе Worker.

Условия до включения возможности:

1. Показывать logN и оценку рабочих буферов до KDF. Заголовок пока не аутентифицирован: его значение — основание ограничить ресурсы, а не доверять файлу. Без отдельного действия для текущей операции уровни 19–20 должны отклоняться. В Worker независимо проверять разрешение и потолок 20 до вызова Typage.
2. Предоставлять режим только на проверенных настольных Chrome/Edge с прямой потоковой записью. На мобильных устройствах и в RAM-fallback оставить 18 и лимит файла 100 МБ. Не запоминать разрешение между операциями, не запускать несколько KDF одновременно и не делать автоматические повторные попытки после сбоя.
3. Не разрешать дорогой KDF автоматически по `navigator.deviceMemory`: по [спецификации W3C](https://www.w3.org/TR/device-memory/) это округлённый объём установленной памяти, а не свободная RAM или лимит процесса. При отсутствии сведений о ресурсах безопасный путь — CLI. Пробное выделение гигабайт памяти тоже не является безопасной проверкой.
4. Сначала провести отдельные последовательные испытания на малых публичных fixtures, на подходящих Windows/macOS ПК. Начальные **испытательные**, а не гарантированные продуктовые бюджеты: до 1536 МиБ суммы RSS браузера для 19 и до 2048 МиБ для 20, с запасом свободной памяти ОС. Перед экспериментом вручную подтвердить не менее 4 ГиБ доступной RAM и отсутствие давления на память; числа уточнить по измерениям. Контроль RSS тестовым драйвером не превращается в надёжный браузерный лимит и не гарантирует предотвращение OOM.
5. Подтвердить SHA-256 восстановления исходных frozen-файлов без их изменения, неверную фразу, повреждение/усечение, отмену во время KDF, перезагрузку, офлайн, сбой Worker и отсутствие ложного успеха/статистики. Отдельно проверить ранний отказ для >20 и отсутствие разрешения в обычном режиме. Не подменять браузерный результат прямым тестом Typage в Node.

В таком режиме отмена KDF требует `terminate()` Worker: scrypt внутри Typage синхронный, сообщение отмены может ждать завершения вычисления. Даже после малых испытаний нельзя обещать гарантированный перехват OOM или полную поддержку всех браузеров. Поэтому это предложение, **не реализованная функция**; текущий безопасный путь для 19–20 — CLI.

Альтернативы рассмотрены: глобальное повышение предела снимает защиту со всех устройств; автоматическая оценка по `deviceMemory` не подтверждает свободную память; серверная расшифровка нарушает локальную модель; собственный KDF/дисковая таблица scrypt либо новая нативная оболочка неоправданно меняют архитектуру. Они не входят в рекомендуемую доработку.
