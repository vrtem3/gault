# Проверки Gault 0.1.1

Проверки запускаются локально; отдельный малый прогон проверяет опубликованный `https://gault.ru`. Используются синтетические файлы. GitHub Actions и CI/CD не используются; публикация кода не запускает тесты или деплой. Файлы и секреты пользователей для тестов не используются. Автоматические тесты не отправляют внешние письма.

## Команды

```bash
cd backend
../.venv/bin/python -m pytest -q
cd ../frontend
npm test
npm run build
npm run test:interop
npm run test:e2e
npm run test:compat
```

Обычный `python3 scripts/run-local.py` и оба профиля Playwright запускают только шифратор на loopback:5173. Кабинет, API, Mailpit, БД и миграции не нужны. На занятом порте локально используется уже запущенный экземпляр; для полностью чистого E2E сначала остановите ручной launcher. Переменная `CI=1` в конфигурации Playwright только запрещает reuse существующего сервера при ручном запуске и не подключает GitHub Actions.

Сохранённые тесты backend и `account.spec.ts` относятся к отложенному этапу и не входят в текущую приёмку шифратора. Стандартный браузерный профиль исключает кабинет. Полный локальный контур можно будет отдельно проверить через `scripts/run-local.py --with-account --test`: только тогда используется изолированная `artifacts/e2e.db`, отличная от `data/gault.db`. По умолчанию он не запускается.

Для шифратора нужны Node.js >=22.12, установленные `frontend/node_modules`, Playwright Chromium и age/rage из `scripts/install-test-tools.py --crypto-only`; Mailpit и backend venv не требуются. Нужен Python 3 для CLI-обвязки; Windows ConPTY-зависимость описана отдельно в [WINDOWS_TESTING.md](WINDOWS_TESTING.md). Криптотесты выполняются последовательно, чтобы не умножать расход памяти KDF. Утилита совместимости использует POSIX PTY либо Windows ConPTY для запроса публичной тестовой фразы и `-o` для бинарного результата; фраза не передаётся в CLI-аргументах. Для ожидаемого пустого выхода rage может не создать файл; interop допускает это только при ожидаемых нулевых данных. Тестовые фразы не являются рабочими секретами.

## Что проверяется автоматически

- **Vitest:** 42 проверки, включая 13 fuzz/property-сценариев. Стандартный scrypt-заголовок; бинарный и пустой roundtrip; неверная фраза, усечение и изменённый байт; защита от слишком высокого KDF; 7776 уникальных слов/103,4 бита; отсутствие Math.random в генерации; zxcvbn для слабых фраз/Unicode; таймзона/ISO-неделя; нулевая отправка без согласия и офлайн; мобильный предел до обработки. Дополнены структурные мутации заголовка и AEAD, ошибки/отмена источника, владение/очистка блоков при write/отмене и отрицательные проверки артефакта.
- **pytest — отложенный backend:** 27 ранее пройденных проверок. Реальные миграции SQLite; Argon2id; полный цикл аккаунта; CSRF/Origin; одноразовость и сроки email-токенов; отзыв сессий; одинаковые ответы email API; редактирование профиля; rate limit; отсутствие секретов в ошибках; IDOR для сессий/подключений; добровольные агрегаты, TTL/дедупликация/лимиты; очистка без SMTP; граница недели, ISO-год и DST; закрытая сводка; SMTP fail/retry, неизменный снимок, отсутствие дублей/конкурентный cron; WAL/foreign_keys; Backup API и восстановленная схема/пользователь. Эти результаты не означают текущую публикацию кабинета.
- **Playwright Chromium:** текущий профиль содержит 55 сценариев шифратора; 3 прежних сценария кабинета исключены. Проверяются 15 frozen-профилей, 25 сбоев, несколько вкладок PWA и ошибки загрузки/очистки кэша. Исходные сценарии: браузер → age/rage и age → браузер с SHA-256; полный офлайн-перезапуск и roundtrip; запрет сети в процессе; слабая фраза; подтверждение экспорта; ошибка записи и фактический abort; отмена с сохранением предыдущей версии дискового файла; неверная фраза/повреждение; защита исходного имени; RAM-download; имитация смартфона и проверка лимита без выделения большого буфера; светлая/тёмная тема, desktop/mobile скриншоты, axe WCAG AA. Добавлены проверка инструкции/конфиденциальности без кабинета и онлайн roundtrip со старым согласием: API и iframe не используются, статистика не отправляется и после close.
- **Независимый interop:** Typage 0.3.1 ↔ age 1.3.2 / rage 0.12.1 для случайных бинарных, пустых и Unicode-данных; 30 чтений 15 frozen-файлов двумя CLI и 6 отрицательных случаев. Это проверка формата библиотекой/CLI; браузерный предел KDF проверяется отдельно. Сравниваются SHA-256. Для тестов используется неизменённый logN=18.

Автоматизация заменяет **только диалог выбора** на `navigator.storage.getDirectory().getFileHandle()`: в основных browser crypto-тестах используются настоящий FileSystemWritableFileStream/OPFS, дисковая запись и закрытие потока. Нативный системный диалог сохранения дополнительно нужно пройти руками на своём ПК. Ошибки диска и write-failure инжектируются отдельно, чтобы проверить отсутствие ложного успеха.

Скриншоты и trace лежат в `frontend/test-results`, HTML-отчёт — `frontend/playwright-report`, оба исключены из Git. Отчёты остаются локальными и автоматически в GitHub не публикуются.

## Ограничения приёмки

- **30 ГБ не подтверждены.** Пробный запуск сообщил QuotaExceededError; по просьбе пользователя большие тесты остановлены, временные входы/блокировки удалены. Повтор без отдельного запроса запрещён. Это не доказательство возможности обработать такой объём.
- Тест не включён в стандартные команды. В скрипте есть явный предохранитель: для размера свыше 200 МБ требуется `GAULT_ALLOW_LARGE_TEST=1`; второе одновременное выполнение блокируется lock-файлом. На этом ПК его не включать.
- Эмуляция мобильного UA/viewport не заменяет реальные iPhone/Android/Safari. 100 МБ — консервативное продуктовое ограничение, а не подтверждённая гарантия каждого устройства. Значения RAM/mobile разрешено понижать через `.env`; повышение свыше 100 требует отдельной доработки после испытаний.
- Основной проверенный браузер — Chromium 156 на macOS arm64. Firefox/Safari и нативная Windows требуют дополнительных реальных прогонов. Windows-обвязка готова; системные диалоги Windows/macOS ещё требуют ручной проверки. Linux остаётся серверной платформой, а пользовательская приёмка нового дополнения — Windows/macOS.
- Docker Engine на текущем ПК отсутствует: production/dev Docker build не проверены. Сохранённый контейнерный вариант относится к будущему полному контуру. На общем сервере используется Nginx без Docker; ранее установленный backend прошёл health-check и `pip check`, но теперь его служба и задания кабинета отключены. Копия закрытой БД прошла `integrity_check`. Публичные DNS/HTTPS и малый прогон проверены отдельно 19.10.2026, см. ниже.
- Публичный репозиторий [vrtem3/gault](https://github.com/vrtem3/gault) хранит код и описание приложения. Workflow CI удалён по решению владельца; результаты платформенных проверок собираются локально и вручную.
- Испытание аварийного восстановления на целевом сервере остаётся открытым. Production SMTP и полный кабинет отложены до отдельного этапа.

Успешные локальные тесты не следует называть завершённой публичной приёмкой всех P0 из ТЗ: отмеченные пункты требуют отдельного оборудования/внешнего окружения.

### Расширенные fuzz-проверки

```bash
cd frontend
npm run test:fuzz
# Увеличенный набор одного seed:
GAULT_FUZZ_SEED=20261019 GAULT_FUZZ_CASES=20000 GAULT_FUZZ_CRYPTO_CASES=64 npm run test:fuzz
# Последовательная кампания на 16 seed с локальными отчётами:
npm run test:fuzz:extended
# Повтор отдельного seed через ту же обвязку:
GAULT_FUZZ_SEEDS=1 GAULT_FUZZ_BUDGET_SECONDS=90 npm run test:fuzz:extended
```

Быстрый профиль использует seed 6791191, 2000 произвольных заголовков, 200 структурных мутаций и 16 генерируемых криптослучаев; предельные значения на seed — 20000/2000/128. Расширенная команда по умолчанию последовательно выполняет 16 разных seed, по 20000 произвольных заголовков, 2000 структурных мутаций и 64 генерируемых криптослучая. Для выбора от 1 до 32 уникальных ненулевых uint32 seed используется `GAULT_FUZZ_SEEDS`, значения разделяются запятыми.

Проверяются соль/wrapped key/MAC и их каноничный base64, BOM/CRLF/лишние станзы/разделители/версия, числа на границе 8192-байтового заголовка, запрет KDF для отвергнутой грамматики, точные границы строк/nonce/64 КиБ и конечные пустые входные блоки. Синтетические контейнеры проверяются на случайные повреждения, усечения, дописанные байты, неверную фразу, перестановку/повтор/удаление блоков и смешивание разных контейнеров. Ошибки чтения до заголовка/nonce и между блоками должны дойти до вызывающего кода. Отказ MAC/unwrap отменяет источник и освобождает его reader. На неверном бесконечном входе проверка прекращает чтение после заполнения префикса; последний полученный блок источника может быть больше оставшейся части префикса, копируются максимум 8192 байта.

| Ограничение кампании | Значение |
| --- | --- |
| Заголовок | 8192 байта |
| Синтетический plaintext | до 196609 байт |
| Один тест / один seed | 30 / 90 секунд |
| Вся кампания | 600 секунд по умолчанию, `GAULT_FUZZ_BUDGET_SECONDS` от 1 до 900 |
| V8 old-space | 384 МиБ на изолят |
| Проверка пика RSS | до 512 МиБ на дочерний процесс Vitest с worker threads |
| Захваченные логи | до 2 МиБ на seed |

Heap-ограничение не является системным лимитом всей памяти процесса. Пик RSS проверяется по `process.resourceUsage().maxRSS` после каждого завершённого seed; это процесс Vitest вместе с его потоками, без отдельного процесса обвязки. Чтение и криптооперации идут последовательно, массовые синтетические контейнеры используют logN=1. Приложение сохраняет шифрование с 18; допустимые 1–18 дополнительно проверяются синтаксически без запуска дорогих KDF.

Обвязка не запускает браузер, сервер, сеть, ручные или большие тесты. Второй экземпляр блокируется `.tools/fuzz-campaign.lock`. SIGINT/SIGTERM и тайм-аут завершают дочерний процесс со всеми worker threads, ожидают его закрытия, сохраняют неположительный статус и удаляют собственный lock. После SIGKILL или аварии ОС оставшийся lock требует проверки записанного PID перед удалением. Отклонение неверных параметров, конкурирующего запуска, остановка SIGINT и тайм-аут проверены автоматически.

Отчёт каждого запуска: `artifacts/fuzz-<timestamp>-<pid>/summary.json`, отдельные `seed-<n>/vitest.json` и `vitest.log`. Записываются параметры, версии, хэши фактически проверенных исходников, счётчики, время и пик RSS. При падении сохраняется первый малый синтетический вход в base64, сценарий и публичная тестовая фраза. Пользовательские файлы/фразы не читаются; отчёты исключены из Git. Seed определяет тестовые данные и мутации; криптографические ключи/соли/nonce Typage остаются случайными, поэтому точный упавший контейнер берётся из сохранённого случая. Для повторения нужны те же параметры и версии. Windows-переменные задаются средствами PowerShell; нативный Windows-прогон отложен.

Фактическая расширенная кампания на macOS arm64 / Node 24.19.0 (19.10.2026): 16/16 seed, 208/208 сценариев, 115,223 секунды; 320000 произвольных и 32000 структурных заголовков, 34752 отказа до KDF, 12624 отклонённых контейнера и 1344 успешных чтения с SHA-256. Дополнительно 128 ошибок источника и 144 отмены/освобождения reader. Пик RSS процесса Vitest — 272,2 МиБ, максимальный вход — 196870 байт. Неразобранных падений нет. Это ограниченный Node-профиль, без заявлений о полном отсутствии DoS или прохождении Windows/больших архивов.

Ручные Windows/macOS-диалоги, реальные смартфоны и остальная матрица размеров остаются открытыми. Отдельный разрешённый автоматический прогон 10 ГБ приведён ниже. При локальной доработке по чек-листу сервер не менялся; последующее подключение публичной HTTPS-поставки описано выше отдельно. Код кабинета и его тесты сохранены для будущего этапа.

### Команды малой проверки ресурсов A5

Сначала запустите шифратор (`python3 scripts/run-local.py --cipher-only` или обычный launcher), затем в другом терминале из `frontend/`:

```bash
npm run test:streaming
```

Это **только 1 и 8 MiB**, независимо от переменной размера большого теста. Вход создаётся реальными случайными блоками по 1 MiB, sparse не используется. Контейнер и восстановленный plaintext записываются настоящими FileSystemWritableFileStream в OPFS. Node SHA-256 получает файл из OPFS ограниченными 512 KiB срезами через локальный тестовый драйвер, не создавая третью host-копию и не накапливая файл целиком. После этого повторно хэшируется host-исходник. Хэширование/предзагрузка Worker между операциями учитываются отдельно от времени шифрования/расшифровки; предзагрузка при отключённой сети обслуживается SW.

Отчёт: `artifacts/streaming-smoke-<OS>-<CPU>.json`. Есть число реальных замеров каждых 250 мс, пиковая сумма RSS процессов Chromium (`ps` на Mac/Linux, WorkingSet64 на Windows), время, размеры, SHA-256, квота OPFS и свободный диск. Сумма RSS может повторно учитывать общие страницы и является оценкой. Отсутствующий/нулевой замер не принимается за успех. Бюджет по умолчанию 2048 MiB, допустимый рост малой матрицы 128 MiB; параметры `GAULT_MEMORY_BUDGET_MB`/`GAULT_MEMORY_GROWTH_MB` фиксируются в отчёте. Бюджет не ослабляет KDF.

До генерации данных стандартная обвязка требует свободное место под 4× максимальный вход + 2 GiB резерва; отдельно проверяется квота OPFS под 3× вход + 1 MiB. Единственный `.tools/large-test.lock` препятствует двум запускам; очищается только собственный временный каталог. Без разрешения размер >200 MB блокируется **до запуска браузера и создания входа**. Малый прогон не доказывает асимптотику больших файлов или приёмку 30 GiB. Новый запрос владельца разрешает отдельный синтетический прогон в пределах 10–15 ГБ; это не разрешение на 30 ГБ.

Для больших файлов создаётся отдельный обычный профиль Chromium внутри временного каталога; профиль пользователя не используется. Фактическая квота проверяется читающим `Storage.getUsageAndQuota` через CDP, при `overrideActive=false`. Переопределение квоты и обход дисковых лимитов не применяются. `navigator.storage.estimate()` сохраняется в отчёте как веб-оценка: Chromium может возвращать искусственное `usage + 10 GiB`, не меняя действительную квоту, см. [официальное описание Chromium](https://groups.google.com/a/chromium.org/g/blink-dev/c/7q0YGQNVkjs/m/-iee67QrBQAJ). Прежняя проверка только этой оценки ошибочно блокировала большой тест до генерации данных.

Предыдущий успешный малый прогон после изменений буферов на macOS arm64/Chromium 156 (19.10.2026): 1 MiB — 7 замеров, пик 703,1 MiB; 8 MiB — 11 замеров, пик 742,8 MiB. SHA-256 обоих восстановленных файлов совпали с исходниками, запросов в окне криптоопераций нет, ошибок измерения нет. Пики зависят от процессов/GC и не являются гарантированным минимальным требованием памяти. После проверки блокировки/прерывания выполнен повторный полный малый прогон; временные входы и lock отсутствуют. Runtime `npm audit --omit=dev`: 0 известных уязвимостей на дату проверки.
